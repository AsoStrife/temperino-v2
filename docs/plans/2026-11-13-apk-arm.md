## Obiettivo

Generare un APK release per smartphone e tablet Android ARM a 32 e 64 bit, contenente la versione corrente dell'app; fornire anche le varianti separate per architettura, più leggere.

## Ambito

- In ambito: build, verifica dell'artefatto, documentazione del comando.
- Fuori ambito: modifiche al codice, incremento versione, nuova firma, pubblicazione, installazione su dispositivi.

## File coinvolti

- `build/app/outputs/flutter-apk/app-release.apk` – artefatto generato, non versionato.
- `build/app/outputs/flutter-apk/app-arm64-v8a-release.apk` – variante ARM64.
- `build/app/outputs/flutter-apk/app-armeabi-v7a-release.apk` – variante ARM32.
- `README.md` – comando per l'APK ARM.
- `docs/knowledge/environment.md` – comportamento della build con librerie native delle dipendenze.
- `docs/README.md` – indice.
- `docs/plans/2026-11-13-apk-arm.md` – piano e verifica.

## Step

### Step 1 – Build e verifica artefatto

- [x] Controllare versione e firma: `2.0.0+1`; manca `android/key.properties`, quindi firma debug prevista dal progetto.
- [x] Eseguire `dart format .` e `flutter analyze` senza issue.
- [x] Eseguire `flutter build apk --release --target-platform android-arm,android-arm64`.
- [x] Generare anche le varianti con `--split-per-abi`, per isolare completamente le architetture native.
- [x] Verificare presenza e dimensione dell'APK, ABI incluse e firma.

**Checkpoint:** ✅ verificato il 2026-11-13. Build combinata e split riuscite. `aapt dump badging`: ABI unica corretta per ciascuno split, `versionName=2.0.0`, `versionCode=2001` ARM64 / `1001` ARM32 (codici derivati da Flutter), `versionCode=1` combinato. `apksigner verify --verbose --print-certs`: firma v2 valida, Android Debug, per tutti e tre gli APK. ARM64: 23.538.697 byte; ARM32: 21.242.229 byte.

### Step 2 – Documentazione e consegna

- [x] Consegnare i collegamenti agli APK con indicazione della firma effettiva.

**Checkpoint:** ✅ verificato il 2026-11-13. Artefatti disponibili in `build/app/outputs/flutter-apk/`; comandi nel README e comportamento ABI/versionCode nella knowledge. Nessuna modifica al codice o commit.

## Deviazioni dalla specifica

Si usa la firma debug di ripiego già configurata; non viene creato un nuovo keystore. Aggiunte le varianti separate perché l'APK combinato include anche librerie x86_64 di dipendenze, pur compilando l'app solo per ARM.

## Rischi / punti aperti

- Nessun dispositivo ARM collegato: l'APK ARM non sarà eseguito sugli emulatori x86_64; il layout è già stato verificato nella precedente sessione in debug.
